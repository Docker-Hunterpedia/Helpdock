# @helpdock/db

The Drizzle schema, the migrations, the row-level security policies, and the
tenant context every query runs inside. Specs: [ARCHITECTURE
§5](../../docs/planning/ARCHITECTURE.md#5-data-model-core-tables) for the data
model, [DOMAIN-RULES §1.3 and
§1.5](../../docs/planning/DOMAIN-RULES.md#1-authorization) for the enforcement
layers and the database roles.

```ts
import {
  appRolePasswordFromUrl,
  assertRuntimeRoleIsSafe,
  createDb,
  runMigrations,
  userBrandRoles,
  withTenant,
} from '@helpdock/db';

await runMigrations({
  migrationUrl: env.DATABASE_MIGRATION_URL,
  appRolePassword: appRolePasswordFromUrl(env.DATABASE_URL),
});

const { db, close } = createDb({ url: env.DATABASE_URL });
await assertRuntimeRoleIsSafe(db); // throws if the role can bypass RLS

const roles = await withTenant(
  db,
  { brandIds: [brandId], departmentIds: 'all', principalType: 'staff', principalId: userId },
  (tx) => tx.select().from(userBrandRoles),
);
```

## Schema

Tables live in `src/schema/`, one file each, re-exported from
`src/schema/index.ts`. M0 has nine:

| Table | Scope | Notes |
|---|---|---|
| `users` | global | Staff accounts. Unique on `lower(email)`, so addresses compare case-insensitively without the `citext` extension. |
| `brands` | global | The tenant. `prefix` is unique, and DOMAIN-RULES §11 keeps it reserved after a brand is deleted. Inserting a row creates that brand's ticket sequence. |
| `user_brand_roles` | tenant | One role per user per brand. `department_ids` null means every department; an empty array means none, which is what an Agent with nothing assigned has. |
| `departments` | tenant | The unit a Team Leader leads and an Agent belongs to. M0-06 needs it to exist so that assignment is real; M1-01 adds business hours, the SLA policy, `on_unassign` and the inbox. Unique on `(brand_id, name)`. |
| `brand_domains` | tenant | Hostnames a brand owns. `domain` is unique install-wide. M0 reads it for Caddy's on-demand TLS check; M5 creates and verifies rows. |
| `settings` | tenant | Primary key `(key, brand_id)`. `value` is JSON, or the `v1.…` envelope for a secret. |
| `audit_log` | tenant | Who did what. `actor_id` is text: a system actor is a job id. |
| `outbox` | tenant | The transactional outbox of DOMAIN-RULES §6. Partial index on the unpublished backlog. |
| `job_receipts` | global | Idempotency keys for consumers with no natural key. |

Ids are **UUIDv7**, generated in `src/uuid.ts`: a 48-bit millisecond timestamp,
a 12-bit counter and 62 bits of randomness (RFC 9562). Node's
`crypto.randomUUID()` is v4 and unordered, which would scatter index inserts, so
it is not used. Ids drawn in the same millisecond still sort in the order they
were drawn.

Some deliberate choices:

- **Install scope is a sentinel brand, not null.** `settings` and `audit_log`
  hold rows that belong to the install rather than to a brand. They carry
  `INSTALL_SCOPE_BRAND_ID` (the nil UUID). A null would never match
  `brand_id = ANY(app.brand_ids)`, so those rows would be unreadable and
  unwritable by the runtime role, and a second policy shape would have to exist
  to let them through. Neither table has a foreign key to `brands`, because the
  sentinel is not a brand; brand deletion removes their rows explicitly.
- **No `key_id` column on `settings`.** The `v1.<keyId>.…` envelope
  `@helpdock/config` writes already names the master key generation, so rotation
  reads it from the value.
- **The ticket sequence is created by a trigger**, not by the caller.
  `brands_create_ticket_sequence` fires after insert and runs
  `helpdock_create_brand_ticket_sequence()`, a `SECURITY DEFINER` function, so
  the sequence exists for every brand row however it was inserted and the
  runtime role still has no DDL rights. The name is
  `brandTicketSequenceName(brandId)`.
- **The unpublished-outbox index is keyed on `id`**, with the partial predicate
  `published_at IS NULL`. The relay reads the backlog in id order, and ids are
  time-ordered, so `published_at` would be a constant column in that index and
  earn nothing.
- **An insert into `outbox` notifies the relay.** The statement-level trigger
  `outbox_notify_relay` (`drizzle/0003_outbox_notify_relay.sql`) runs
  `pg_notify('outbox', '')`, which Postgres delivers on commit, so a rolled-back
  transaction wakes nobody. The relay in [`@helpdock/jobs`](../jobs/README.md)
  listens on that channel; the payload is empty because the relay reads the
  table and needs a nudge, not a list.

## Tenant context

Row-level security is the layer that still holds when a guard is forgotten
(DOMAIN-RULES §1.3). Every tenant table has the same four policies, generated by
`tenantPolicies` in `src/rls.ts` and committed as
`drizzle/0002_tenant_rls_policies.sql`:

```sql
brand_id = ANY (nullif(current_setting('app.brand_ids', true), '')::uuid[])
```

and, for a department-scoped table (none yet; tickets arrive in M1):

```sql
AND (coalesce(nullif(current_setting('app.all_departments', true), '')::boolean, false)
     OR department_id = ANY (nullif(current_setting('app.department_ids', true), '')::uuid[]))
```

Without a context the setting is null, `= ANY(null)` is null, and nothing is
visible: the failure mode is "nothing", never "everything".

`withTenant(db, context, fn)` opens a transaction, sets `app.brand_ids`,
`app.department_ids`, `app.all_departments`, `app.principal_type` and
`app.principal_id` with `set_config(…, true)`, and runs `fn` inside it. The
values are validated (`brandIds` and `departmentIds` must be UUIDs) and then
bound as query parameters, never pasted into SQL. The settings are local to the
transaction, so the next request on the same pooled connection starts with none
of them.

`withSystem(db, brandId, fn)` is the worker's context: one brand, every
department, `principal_type = system` (DOMAIN-RULES §1.4). A job with an id of
its own passes it through `systemContext(brandId, jobId)` to `withTenant`, so
the audit trail names the job. A job that needs several brands enqueues one
child job per brand.

What the policies enforce is that a transaction sees only the brands its context
names. What brands a context may name is layer 1's job: the guard on the route
(DOMAIN-RULES §1.3). In particular, a context that includes
`INSTALL_SCOPE_BRAND_ID` can read *and write* install-wide `settings` and
`audit_log` rows, so a brand request must not be given it unless the route is an
install-admin route. Row-level security is the layer that survives a forgotten
guard; it is not a substitute for one.

## Database roles

| Role | Used by | Privileges |
|---|---|---|
| owner (`DATABASE_MIGRATION_URL`) | migrations only | Owns every table; needs `CREATEROLE` the first time |
| `helpdock_app` (`DATABASE_URL`) | every runtime query | `NOSUPERUSER NOBYPASSRLS NOCREATEDB NOCREATEROLE LOGIN`, DML only, owns nothing |

The first migration provisions `helpdock_app` if it does not exist, with the
password `runMigrations` puts in the `helpdock.app_password` session setting —
derived from `DATABASE_URL` by `appRolePasswordFromUrl`. An existing role is
left exactly as it is, password included.

Later tables are granted to `helpdock_app` through `ALTER DEFAULT PRIVILEGES`,
which is recorded against the role that ran the first migration. Migrations must
keep running as that role; a different owner would create tables the runtime
role cannot reach, and the api would fail loudly on the first query against one.

`assertRuntimeRoleIsSafe(db)` is what api boot calls before serving (wired up by
M0-04). It throws when the connected role is a superuser, has `BYPASSRLS`, or
owns a table in the schema — including through a role it can `SET ROLE` to. A superuser bypasses policies
whatever a table says, which is why this check exists and why no test can prove
`FORCE` against one.

## Migrations

Generated SQL lives in `drizzle/` and is committed. `runMigrations` applies it,
and api boot calls it from M0-04 onwards: it connects as the owner on a single
connection, takes a Postgres advisory lock, runs Drizzle's migrator, releases the
lock, and returns the migrations it applied. Several replicas may call it at once; the lock serialises
them and every replica but one applies nothing.

```bash
pnpm --filter @helpdock/db gen:migration   # drizzle-kit generate, after a schema change
pnpm --filter @helpdock/db gen:rls         # append the missing policies to that migration
```

`gen:rls` appends the policies of any `TENANT_TABLES` entry that has none yet to
the newest migration — the one `gen:migration` has just written for that table.
They belong together because migrations are forward-only: a policy that ran
before its own table existed would fail on a fresh database. `rls.test.ts` fails
while a tenant table has no policies in any committed migration, and fails again
if a policy ends up ahead of its `CREATE TABLE`.

`drizzle-kit migrate` and `push` are not part of any workflow: nothing but
`runMigrations` applies migrations, so the advisory lock is never bypassed.

## Adding a tenant table

1. Add the table in `src/schema/`, with `brandId: uuid('brand_id').notNull()`
   and, if it is ticket-scoped, a denormalised `department_id`.
2. Add it to `TENANT_TABLES` in `src/rls.ts` (or to `GLOBAL_TABLES`, with the
   reason it needs no policy — `src/schema/index.test.ts` fails if it is on
   neither list).
3. `pnpm --filter @helpdock/db gen:migration` for the table, then
   `pnpm --filter @helpdock/db gen:rls`, which appends its policies to that same
   migration. Rename the generated file after what it does and commit it.
4. **Add it to the negative suite** in `src/rls.integration.test.ts`: one
   fixture row, and the cross-brand read, insert, update, delete, subquery and
   join cases run against it automatically. The suite fails until the fixture
   exists, which is how DOMAIN-RULES §1.6 stays true.

`departments` is the worked example: `0005_departments.sql` carries the
`CREATE TABLE` and its four policies in one file, and `rls.integration.test.ts`
gained one fixture row. `0006_contacts_and_accounts.sql` is the same shape for
five tables at once.

## Tests

`src/*.test.ts` are unit tests and need nothing installed. `src/*.integration.test.ts`
start a real `pgvector/pgvector:pg17` with Testcontainers and cover the
migrations, the negative suite and the settings store; they skip themselves and
say so when Docker is not running.

## Known gaps

- `tickets.contact_id` has no foreign key to `contacts`. M1-02 creates the
  column and M1-04 created the table; the constraint belongs to whichever of the
  two lands second.

- A brand-scoped `PostgresSettingsStore` reads and writes only its own rows. It
  does not fall back to the install-wide value for a key a brand has not
  overridden; that resolution rule belongs to the milestone that puts per-brand
  settings in admin.
- Nothing drops a brand's ticket sequence yet. Brand deletion and retention are
  DOMAIN-RULES §11, and arrive with the maintenance jobs.
